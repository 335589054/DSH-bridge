## WorkBuddy × DeepSeek Harness 接入项目（workbuddytoharness）

- 目标：DSH 通过插件调用 WorkBuddy 订阅模型。路线：`dsh 插件（LLM adapter）+ 本地 bridge + workbuddy 插件（控制面）`。
- 关键事实：上游 `https://copilot.tencent.com/v2/chat/completions`（国际版 `www.workbuddy.ai/v2`），OpenAI Chat Completions 协议、仅流式；必需头 `X-User-Id / X-Domain / X-Product: SaaS / X-IDE-Type: WorkBuddy / UA WorkBuddy/5.5.6`，缺失报 10085；无 `/models`（目录来自 `GET /v3/config`）、无 embeddings。
- 本机实测：`%LOCALAPPDATA%\CodeBuddyExtension\Data\Public\auth\workbuddy-desktop.info` 已是 AtRest AES-256-GCM 信封，进程外不可读。
- **v0.2 决策（用户要求）**：不申请 API Key，改为「本机抓包 + 转发」——mitmproxy 旁路读取客户端请求头 → `POST /capture/session` → bridge 内存会话 → 转发时整组复用（Auth/X-*/Cookie/UA）。
- 抓包层：`packages/capture/mitm_addon.py`（只读头、sha256 去重、401 清缓存）；桥新增 `/capture/session`、`/capture/status`、`DELETE`，双钥匙 `.bridge-token` / `.capture-key`，头白名单在 `session.mjs`。
- 参考实现：`Ianzhyh/workbuddy-to-dsh`（8790）、`Acoder416/dsh-plugin-workbuddy-gateway`（18088）、`@magpie-community/opencode-workbuddy-auth`。

## 凭证调研：WorkBuddy 登录态无法直读（结论用，勿重复踩）

用户要求「用当前对话的凭证」真跑 DSH。结论：**拿不到明文，只能抓包或 API Key**。证据链：
- `workbuddy-desktop.info` → `auth.accessToken = {$wbEncrypted:1, envelope}`，envelope 解出来是 `{suite:1,keyId,nonce,authTag,ciphertext}`，AES-GCM；accessToken 有效期到 2026-11 之后（expiresAt 1794802131571）。
- `~/.workbuddy/keyblob` 是明文 JSON，但只有 `slots[0].type = "static-v1"` + `protectorKeyId` + `wrapped`（wrapped 本身又是一层同格式 envelope，ciphertext 44 字符 ≈ 32 字节 AES key）。**static-v1 的保护器密钥不在任何用户可读文件里（在 app.asar 里），不去逆向。**
- 近似可行但都排除了：
  - `127.0.0.1:46285` 是 CodeBuddy Remote Control 网关（`Authorization: Bearer $CODEBUDDY_GATEWAY_PASSWORD` 可过鉴权），但端点是 `POST /api/v1/runs` + `GET /api/v1/runs/:id/stream`，**是把消息注入当前会话**（`/api/v1/status` 里 `activeSessionId` 就是本对话 sessionId、`busy:true`），不是 chat completions。
  - `127.0.0.1:6322/skills/vlm/chat` 是视觉技能，`WORKBUDDY_VLM_AUTH_TOKEN` 三种头都 401，且不是通用文本端点。
  - `CODEBUDDY_GATEWAY_PASSWORD` 直接打 `copilot.tencent.com/v2/chat/completions` → 401（openresty）。
- 抓包前置条件变差了：`~/.mitmproxy` 目录已被清空，`ca.exists=false`、证书库里也没有 mitmproxy 根证书 → 真抓包要重新 `POST /setup/ca`；系统代理仍被沙箱 reg.exe 黑名单挡，只能用户手动开。

## 网关上游（会污染会话）：实现 + 两个坑

- bridge 新增 `WORKBUDDY_GATEWAY_URL` / `WORKBUDDY_GATEWAY_AUTH`：把 OpenAI chat 请求翻成
  `POST {gw}/api/v1/runs`（body `{id, type:"text", text}`）+ `GET {gw}/api/v1/runs/:runId/stream`
  再转回 OpenAI chunk。`health.mode` 显示 `gateway`，该模式不依赖上游凭证，`/v1/models` 走静态表。
- 网关就是 WorkBuddy 主进程（占 46285），`Bearer $CODEBUDDY_GATEWAY_PASSWORD` 鉴权；注入落在
  `activeSessionId`（日志 `isShared=true`），也就是**当前对话**。
- SSE 协议实证：`event: message`，data 里 `status` = `accepted` / `streaming`（`content.chunk` 增量）
  / `completed`（`content.markdown` 全文）/ `error`，收尾 `event: done`。入站只认 `text` 字段
  （`payload.text ?? body.text ?? body.prompt`），写 `content` 等于空 prompt，会 202 后秒结束。
- **坑 1（严重）**：DSH 除用户消息外还会发「会话标题生成」和带 `<system-reminder>` 的请求，
  初版没过滤，直接被注入当前会话。已加 `auxKind()` 拦截（title / system-reminder / compact / >4000 字），
  本地返回 `DSH × WorkBuddy` 等假应答——实测 curl 两条都被 `skip aux` 挡住。
- **坑 2**：排队中的 run 不在 `activeTasks`，`POST /api/v1/runs/:id/cancel` 返 404 但 run 仍
  `active:true`，**取消不掉**，只能等会话空闲后自己跑。

## CA 装不进系统证书库（环境策略硬拦）

- mitmdump 12.2.3 可用；`POST /capture/start` 起在 8899 正常（`{"proxy":false}` 不动系统代理）。
- 首次起 mitmdump 会生成 `~/.mitmproxy/mitmproxy-ca-cert.cer`（1172B），这步 OK。
- 但写根证书库一律被强杀：`certutil -user -addstore`（含 `C:/Windows/System32/certutil.exe` 完整路径）
  = SIGTERM；`Import-Certificate` = "此操作中不允许使用 UI"；`X509Store.Add()` 进程终止（catch 都进不去）。
  只读打开 store 正常（53 张）。→ CA 只能用户手动双击装，或用 `NODE_EXTRA_CA_CERTS`。

## 修掉「注入的不是用户那句话」的 bug（网关模式核心缺陷）

- 现象：DSH 发「你好」，桥也确实注入了，但会话里出现的是 `<system-reminder>` 正文，用户那句话消失。
- 根因：`lastUserText()` 取 `messages` 里**最后一条 user**，而 DSH 把
  `<system-reminder>…</system-reminder>` 追加在用户消息之后（有时独立成一条 user）。
  于是抓到的是提醒正文。上一轮加的 `auxKind` 更糟：直接判定 `system-reminder` 并整条 skip，
  真实提问被静默丢弃。
- 修法（`packages/bridge/server.mjs`）：拆出 `messageText()` / `stripReminders()` / `lastRawUserText()`；
  `lastUserText()` 改为「从后往前找，剥掉提醒块后仍非空」的 user 消息；
  `auxKind()` 判据分两层：`raw` 为空→empty，`raw` 非空但剥完为空→system-reminder（纯提醒），
  否则才按正文判 title/compact/oversized。
- 验证（**不污染会话的做法**，以后沿用）：`.cache/dummy-gw.mjs` 假网关（POST /api/v1/runs 记 body、
  GET /stream 回 accepted/streaming/completed/done），bridge 用 `WORKBUDDY_PORT=8791` 另起一份指向它，
  `.cache/gw-injections.jsonl` 落实际注入的 body。5 个用例全过：
  `你好`+独立提醒条→注入「你好」；纯提醒条→skip；标题→skip；提醒嵌同行→注入「帮我看看这个报错」；多轮→注入「第二句」。
  **要点：bridge 端口可用 `WORKBUDDY_PORT` 改，不必停正式实例。**

## 证书随包 + 使用指南 + 快捷使用（0.4.0）

**动机**：用户要求「把安装需要的证书打包进去、写使用指南、实现快捷使用」。
旧流程是「先跑一次抓包生成 CA → 再手动装证书」，两步都可能卡住。

### 随包 CA
- `packages/bridge/certs/`：openssl 预生成 `mitmproxy-ca.pem`（私钥+证书，RSA2048/SHA256/5y）、
  `mitmproxy-ca-cert.pem`、`mitmproxy-ca-cert.cer`（DER）、`install-ca.cmd`、`uninstall-ca.cmd`、`README.md`。
  CN = `WorkBuddy Bridge Local CA`（不用 mitmproxy 默认 CN，避免与用户自己的 mitmproxy CA 混淆）。
- `admin.mjs`：`seedCa()` 把 certs/ 同步到运行期 `bridge/.ca/`；mitmdump 一律带
  `--set confdir=<bridge>/.ca`。装证书不再依赖先生成，也不碰 `~/.mitmproxy`。
- 检测：`certutil -user -store Root <CN>`；命中 CN 即算已装，指纹不一致只记日志
  （拦人会让人彻底没法抓包）。
- `installCa()` 不再需要先起 mitmdump；certutil 失败 → `Import-Certificate` 兜底 →
  仍失败回 `{manual:true, file, script, error}`，UI/CLI 直接给 `install-ca.cmd` 路径。
- `startCapture()` 前置检查：证书没装直接拒绝（`needsCa:true`），否则用户只看到一片 TLS 错误。
  逃生门 `WORKBUDDY_SKIP_CA_CHECK=1`（证书装在「本地计算机」库时查不到）。

### 健壮性（这轮新发现的坑）

## 0.5.6：SPAWN_TIMEOUT 根因——ELECTRON_RUN_AS_NODE 环境中毒（真实事故闭环）

用户在 DSH 面板点「开始抓包」→ 杀掉 WorkBuddy → 重新拉起 → 报「20 秒内没检测到进程」，
失败回滚的还原启动也秒死，用户只能手动重开客户端（用户确认）。

**取证链**：WorkBuddy 进程全在（20:06:49 起）但根进程父是 Dasktop.exe（用户手动起的），
bridge 自己 spawn 的那份根本没活；无害实验复现——带 `ELECTRON_RUN_AS_NODE=1` spawn
WorkBuddy.exe，1.5 秒内进程消失。根因：DSH 拉起 bridge 时注入 `ELECTRON_RUN_AS_NODE=1`
（为了让 Electron exe 按 Node 跑），`launch()` 把自己的环境**整份复制**给 WorkBuddy.exe
（同为 Electron）→ 以纯 Node 模式启动、无参数立即退出。旧 bridge（自托管/沙箱拉起）没有
这个变量，所以以前测试抓包没暴露。

**修复**：`workbuddy-client.mjs` 的 `launch()` 加 `CHILD_ENV_STRIP`（ELECTRON_RUN_AS_NODE /
ELECTRON_NO_ATTACH_CONSOLE / ELECTRON_ENABLE_LOGGING），两条路径（代理接管 + 还原）共用。
AGENTS.md 硬性决策 11；GUIDE 故障排查补条目。产物 `dist/workbuddy-dsh-plugin-0.5.6.zip`。

先结束旧 bridge（已替用户杀掉 29320，8790 已释放）→ 双击 `packages/bridge/start.cmd`。
